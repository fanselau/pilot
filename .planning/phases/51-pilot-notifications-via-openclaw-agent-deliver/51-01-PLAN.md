  <files>src/core/types.ts, src/core/db.ts, test/core/db.test.ts</files>
  <action>
Define a canonical OpenClaw route contract and persist it where Pilot already stores notification intent.

1. In `src/core/types.ts`, add a dedicated route type:
   - `OpenClawDeliverRoute` with exact shape `{ kind: 'openclaw-agent-deliver', agentId, channel, to, accountId? }`.
   - Extend `Project` with `notifyOpenClawRoute: OpenClawDeliverRoute | null`.
   - Extend `Job` with `notifyRoute: OpenClawDeliverRoute | null` (queue-time snapshot).

2. In `src/core/db.ts`, add additive schema migration columns:
   - `projects.notify_openclaw_route TEXT DEFAULT NULL`
   - `jobs.notify_route TEXT DEFAULT NULL`
   Keep existing callback columns (`callback_session_key`, `callback_url`) intact for backward compatibility.

3. Update row mappers and writes:
   - Parse both new JSON columns safely; invalid JSON becomes `null` (never throw).
   - Extend `addJob()` signature to accept optional `notifyRoute` snapshot and write `notify_route`.
   - Add project helpers to set/clear route (single update API that accepts route or null).

4. Add/adjust db tests in `test/core/db.test.ts`:
   - project route persists and round-trips through `getProject()`
   - job route snapshot persists and round-trips through `getJob()`
   - malformed stored JSON degrades to `null` without crashing

Why: delivery logic cannot be reliable until the route contract is first-class in storage.

<task type="auto">
  <name>Task 2: Implement strict route resolver (structured first, legacy derive second)</name>
  <files>src/core/notify-route.ts, test/core/notify-route.test.ts</files>
  <action>
Create a dedicated routing module that resolves and validates deliver targets before any transport code runs.

1. Create `src/core/notify-route.ts` with exported helpers:
   - validate structured route objects (required fields + kind)
   - derive route from known legacy formats only (e.g., full `agent:...` session-key shapes)
   - resolve order: job snapshot route -> project route -> safe legacy derive -> explicit config error

2. Enforce strictness:
   - plain `main` / owner-only values are not enough to derive reply route (`channel` + `to`) and must return actionable error
   - do not add fuzzy regex guesses for unknown owner formats
   - include clear error codes/messages that callback/CLI can surface directly

3. Add focused tests in `test/core/notify-route.test.ts`:
   - structured route success
   - structured route missing field failure
   - legacy group key derive success
   - legacy DM key derive success
   - unknown/plain legacy value failure
   - precedence: structured route wins over legacy parseable value

Why: this isolates all routing risk into one deterministic boundary and prevents wrong-chat delivery.
  </action>
  <verify>`npx vitest run test/core/notify-route.test.ts` passes with success/failure coverage for structured + legacy inputs.</verify>
  <done>Notify-route module produces canonical routes for valid inputs, rejects ambiguous inputs with explicit errors, and has dedicated tests covering group and DM derivation paths.</done>
