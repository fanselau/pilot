  <files>src/core/queue-store.ts</files>
  <action>
Modify the `saveQueue` function to implement atomic writes with backup:

1. **Backup before write:** Before writing, copy current queue.json to queue.json.bak using `copyFileSync` (sync to ensure backup completes before mutation). Skip if queue.json doesn't exist yet.

2. **Atomic write:** Replace `writeFile(config.queueJsonFile, ...)` with:
   - Write to `${config.queueJsonFile}.tmp` using `writeFileSync` (sync for crash safety)
   - Call `fsyncSync` on the file descriptor to flush to disk (open, fsync, close)
   - `renameSync(tmpPath, config.queueJsonFile)` — rename is atomic on Linux same-filesystem

   Import `writeFileSync, renameSync, copyFileSync, openSync, fsyncSync, closeSync` from `node:fs`.

3. **Corruption recovery in loadQueue:** Wrap `JSON.parse(raw)` in a recovery chain:
   - Try parsing normally
   - If parse fails: try trimming trailing garbage (truncated write) — strip everything after last `}`
   - If still fails: try reading queue.json.bak and parsing that
   - If bak also fails: return empty queue `{ version: 1, items: [], history: [], completedIds: [] }`
   - Log to stderr on any recovery path: `[queue-store] Recovered from corrupt queue.json` or `[queue-store] Using backup queue.json.bak`

4. **Raise history cap:** Change `MAX_HISTORY` from 100 to 200 per requirements.

Do NOT change the locking mechanism itself (proper-lockfile stays). Do NOT change any function signatures. Do NOT add new exports beyond what's needed.

Note: Use `node:fs` sync methods for the write path (writeFileSync, renameSync, copyFileSync, fsyncSync) because crash safety requires sync operations. The async `writeFile` + `rename` pattern has a window where both old and new data could be lost. The lock is already held during write so blocking is acceptable.
