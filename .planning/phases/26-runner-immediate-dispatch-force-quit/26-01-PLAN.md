<objective>
DB layer: transactional job claiming with project serialization + force-quit state transitions.

Purpose: The runner's current `getNextPending()` has no project serialization — it can return a second job for the same project while one is already running. This plan replaces it with an atomic `claimNextLaunchable()` that holds a transaction during SELECT + UPDATE, preventing any race condition. Also adds `forceQuitJob()` for consistent state transitions when an operator terminates a job.

Output: Three new exported functions in db.ts: `claimNextLaunchable`, `forceQuitJob`, `getRunningJobsByProject`.
</objective>

  <action>
Add `claimNextLaunchable()` function to db.ts. This replaces `getNextPending()` in the runner's dispatch path. It must:

1. Run inside a `db.transaction()` block (better-sqlite3 synchronous transactions)
2. Within the transaction:
   a. Query for projects that already have a running job:
      ```sql
      SELECT DISTINCT project FROM jobs WHERE status = 'running'
      ```
   b. Query for the next pending job whose project is NOT in that running set:
      ```sql
      SELECT * FROM jobs
      WHERE status = 'pending'
        AND project NOT IN (SELECT DISTINCT project FROM jobs WHERE status = 'running')
      ORDER BY priority DESC, created_at ASC
      LIMIT 1
      ```
   c. If found: immediately UPDATE that job to `status = 'running'`, set `started_at = datetime('now')`, increment `attempts = attempts + 1`
   d. Return the Job object (using existing `rowToJob` mapper)
3. If no eligible job found: return null

The transaction ensures atomic read-then-claim: no two runner processes can claim the same job or violate project serialization.

Also add `getRunningJobsByProject(project: string): Job[]` — returns all jobs with status='running' for a given project. Used by the runner to verify serialization state:
```sql
SELECT * FROM jobs WHERE status = 'running' AND project = ?
```

Export both functions in the exports block at the bottom of db.ts.

IMPORTANT: Do NOT remove or modify the existing `getNextPending()` function — it may still be used in tests and other places. Add the new functions alongside it.

  <action>
Add `forceQuitJob(id: string, source: 'cli' | 'tui', reason?: string)` to db.ts.

This function handles the DB-side of a force-quit:
1. Look up the job by ID. If not found or not in status='running': return early (noop — reconciler may have already cleaned it).
2. Build error message: `"Force-quit by operator via ${source}: ${reason ?? 'no reason given'}"` 
3. In a transaction:
   a. UPDATE jobs: `status = 'failed', completed_at = datetime('now'), error = <message>`
   b. UPDATE job_steps: for all steps with status='running' belonging to this job, set `status = 'failed', completed_at = datetime('now'), verdict_reason = <message>`
4. Return `{ ok: true, job: updatedJob }` on success, `{ ok: false, reason: string }` if job not found or wrong status.

Return type:
```typescript
interface ForceQuitResult {
  ok: boolean;
  reason?: string;  // populated when ok=false
  job?: Job;        // populated when ok=true
}
```

Export `ForceQuitResult` as a type export and `forceQuitJob` as a value export.

NOTE: This function only updates DB state — it does NOT kill any process. Process termination is handled separately in runner.ts (Task 1 of Plan 02). The separation is intentional: DB state update is always safe; process kill may fail.
