    - Test 5: step `shortSummary` fallback order is assistant text → verdictReason → error → null
    - Test 6: last assistant messages are capped at 3, newest first, skipping duplicates/empty noise
    - Test 7: missing session/title data degrades cleanly instead of throwing
  </behavior>
  <action>
    Per D-01, D-02, D-03, D-05, D-11, and D-12, create `src/core/job-summary.ts` as the single shared summary builder.

    Export these exact interfaces from the new file:
    - `StepExecutiveSummary`
    - `JobExecutiveSummary`

    Implement `buildJobExecutiveSummary(job: Job, steps: JobStep[]): JobExecutiveSummary` with these concrete rules:
    - `what`: use the final useful assistant text from the running step or last completed step when available; otherwise fall back to `buildJobWhy(job).what`
    - `why`: `buildJobWhy(job).why`
    - `next`: `buildJobWhy(job).next`
    - `statusBadge`: `buildJobWhy(job).badge`
    - `outcome`: map `completed -> success`, `failed/cancelled -> failure`, `completed_pending_review -> review_pending`, `review_hold -> review_hold`, else `unknown`
    - `currentOrFinalStep`: running step first, else last step by `stepIndex`, else `null`
    - `failureReason`: failed-step `verdictReason` → `job.error` → current/final-step `verdictReason` → `null`
    - `judge`: build from `buildJudgeSignal(job)` with `{ verdict, confidence, reason, badge }`, else `null`
    - `verification`: normalize `buildJudgeSignal(job).verification` into the required object, else `null`
    - `commitDelta`: reuse the current `gitBaseCommit` / `gitHeadCommit` logic from `src/commands/log.ts`
    - `observability`: `buildJobObservability(job)`
    - `drilldown.summaryCommand`: `pilot summary ${job.id}`
    - `drilldown.logCommand`: `pilot log ${job.id}`
    - `drilldown.reviewCommand`: include `pilot review ${job.id} --approve` for `completed_pending_review` and `review_hold`
    - `drilldown.unblockCommand`: include `pilot unblock "${job.project}"` for failed/cancelled jobs when the project is expected to be blocked

    For step summaries:
    - resolve the session by `step.sessionId` first, then `findSessionByTitle(step.sessionTitle ?? '')`
    - call `getLatestUsefulAssistantTextMessage()` for the resolved session
    - set `shortSummary` using the strict fallback order from D-03
    - build `evidence` from only these inputs: `step.verdictReason`, `step.error`, verification `artifactPath`, latest assistant preview
    - keep `evidence` compact and deterministic; never include raw tool output or multiline transcript dumps

    For `lastAssistantMessages`:
    - scan relevant step sessions newest-first
    - keep max 3 unique non-empty assistant text entries
    - store `{ stepIndex, sessionTitle, text }`

    For `keyArtifacts`:
    - start with `verification.artifactPath` when present
    - then extract obvious repo-relative path-like tokens from strong assistant messages only
    - dedupe and cap the list at 5 entries

    Add `test/core/job-summary.test.ts` covering all behaviors above. Keep the tests deterministic by mocking `buildJobObservability`, `findSessionByTitle`, and `getLatestUsefulAssistantTextMessage` where appropriate.
  </action>
