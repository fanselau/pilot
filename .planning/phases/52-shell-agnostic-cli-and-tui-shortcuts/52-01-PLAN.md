  **In `src/core/delegate.ts`, rewrite `resolveOpencodeBinary()`:**

  The current code always returns `candidates[0]` without checking if it exists. Fix:

  1. Keep the candidates array: `[path.join(home, '.opencode', 'bin', 'opencode'), 'opencode']`.
  2. Loop through candidates. For absolute paths, use `accessSync(candidate, constants.X_OK)` to check existence and executability. For bare command names (no `/`), use `Bun.which(candidate)` (or `which` from `node:child_process` via `execaSync('which', [candidate])`) to check PATH resolution. Return the first one that resolves.
  3. If no candidate resolves, return `'opencode'` as last resort (will produce a clear ENOENT at spawn time).
  4. Export `resolveOpencodeBinary` so it can be tested and used by doctor.

  **Use this pattern** (avoid adding new dependencies):
  ```typescript
  import { accessSync, constants } from 'node:fs';

  export function resolveOpencodeBinary(): string {
    const home = process.env['HOME'] || process.env['USERPROFILE'] || '';
    const candidates = [
      path.join(home, '.opencode', 'bin', 'opencode'),
      'opencode',
    ];
    for (const candidate of candidates) {
      if (candidate.includes(path.sep) || candidate.startsWith('.')) {
        // Absolute/relative path — check filesystem
        try {
          accessSync(candidate, constants.X_OK);
          return candidate;
        } catch { continue; }
      } else {
        // Bare command name — check PATH via which
        try {
          const { stdout } = execaSync('which', [candidate], { reject: false });
          if (stdout?.trim()) return stdout.trim();
        } catch { continue; }
      }
    }
    return 'opencode'; // fallback — will ENOENT with clear message
  }
  ```

  Note: Use `execSync` or `execaSync` for `which` — this is called once during spawn setup, not in a hot path. Or better: use `Bun.which('opencode')` if available, falling back to `execaSync('which', ...)`.

  **In `src/commands/service.ts`, fix the unit file generation (line ~28-44):**

  The current code bakes `process.argv[1]` and `process.execPath` directly into the unit, which go stale after rebuilds. Fix:

  1. Instead of `process.argv[1]`, resolve the pilot binary to its real path using `fs.realpathSync(process.argv[1])`. This follows any symlinks to the actual file on disk.
  2. Instead of baking `process.execPath` (absolute path to current bun/node), use `#!/usr/bin/env bun` shebang pattern. The unit's ExecStart should just run the script directly (since it has a shebang) or use `/usr/bin/env bun <script>` if needed.
  3. For the PATH, instead of baking the entire current PATH, use a minimal stable PATH that includes the key directories. Pattern:
     ```
     Environment=PATH=/usr/local/bin:/usr/bin:/bin:${os.homedir()}/.local/bin:${os.homedir()}/.bun/bin
     ```
     This covers: system bins, user local bin (common for pip/bun/etc), and bun's install dir. Also append any FNM or NVM paths if detected from current env:
     ```typescript
     const stablePath = [
       '/usr/local/bin', '/usr/bin', '/bin',
       path.join(home, '.local', 'bin'),
       path.join(home, '.bun', 'bin'),
     ];
     // Include fnm/nvm paths if present
     const currentPath = process.env.PATH ?? '';
     for (const segment of currentPath.split(':')) {
       if (segment.includes('fnm') || segment.includes('nvm') || segment.includes('.cargo')) {
         if (!stablePath.includes(segment)) stablePath.push(segment);
       }
     }
     ```
  4. Change ExecStart to use `/usr/bin/env bun` instead of the absolute interpreter path:
     ```
     ExecStart=/usr/bin/env bun ${realpathPilotBin} run --daemon
     ```
     This way, even if bun is upgraded (new version at same PATH location), the service still works.
  5. Add a comment at the top of the unit with the generation timestamp so operators can see when it was last regenerated.
