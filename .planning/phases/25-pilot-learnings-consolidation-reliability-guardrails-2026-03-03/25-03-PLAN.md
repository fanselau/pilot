Add a new helper function `isJobStale(job: Job): boolean` BEFORE the `statusCommand` function.

**Staleness criterion (must match exactly):** A job is stale when:
1. It has `sessionTitles` recorded (not null/empty) — if no titles, the job may be starting, return false
2. The most-recent title (last element of the parsed JSON array) maps to a real session ID via `findSessionByTitle(lastTitle)` — if not found, return false (session may still be appearing)
3. That session ID exists in opencode DB AND `isSessionActive(sessionId)` returns **false** — the session has ended

Only when all three conditions hold (titles exist, session found, session inactive) is the job considered stale. This is the **only** implementation that matches the key_link intent.

```typescript
/**
 * Status integrity check: determine if a 'running' job has no backing opencode session.
 *
 * A job is stale when its most recent session title maps to a session in opencode DB
 * that is no longer active (isSessionActive returns false).
 *
 * Returns false (not stale) when:
 * - No session titles recorded yet (job may just be starting)
 * - Most recent session not yet in opencode DB (session may still be initialising)
 * - On any parse/read error (err on side of caution)
 */
function isJobStale(job: Job): boolean {
  if (!job.sessionTitles) return false; // No titles yet — job may be starting

  try {
    const titles = JSON.parse(job.sessionTitles) as string[];
    if (titles.length === 0) return false;

    // Check ONLY the most recent session title (last element)
    const lastTitle = titles[titles.length - 1];
    const sessionId = findSessionByTitle(lastTitle);
    if (!sessionId) return false; // Not in opencode DB yet — might be initialising

    // Session exists in opencode DB — check if it's still active
    // isSessionActive returns false when the session has ended
    return !isSessionActive(sessionId);
  } catch {
    return false; // Err on side of caution — don't show false stale warnings
  }
}
```

Write a substantive document (60+ lines) covering the four operational incidents:

1. **Ghost-running jobs** — DB shows `running`, backing opencode session ended, job never advances
   - Root cause: runner event loop has no mechanism to detect or reset jobs whose sessions exited unexpectedly; `markFailed`/`markCompleted` only runs if `launch()` completes normally
   - Mitigation: `reconcileStaleJobs()` in db.ts + startup and periodic reconciliation in runner.ts (Phase 25, plans 25-01, 25-02); status integrity check in status.ts (plan 25-03)

2. **Same-project concurrent launches** — two jobs for the same project started in parallel causing git conflicts and STATE file corruption
   - Root cause: `getNextPending()` returns oldest pending job regardless of same-project running state; runner's `this.activeJobs.has(job.id)` guard only prevents exact duplicate ID, not same-project
   - Mitigation: Same-project serialization guard in `run()` loop checking `this.activeJobs` for same project before launching (Phase 25, plan 25-02)

3. **Runner reload killing in-flight execution** — SIGHUP or restart terminates a running delegation step mid-way, leaving job in partial state
   - Root cause: `shuttingDown = true` interrupts `spawnAndWait()` immediately; job gets cancelled not failed; DB shows `cancelled` which loses context
   - Mitigation: SIGHUP triggers drain mode (existing SIGHUP handler drains current steps before re-exec); documented as known behavior — operators should use `pilot stop` then restart rather than SIGKILL. Graceful reload contract documented in this file.

4. **Misleading status output** — `pilot status` showed ghost-running jobs as healthy active jobs
   - Root cause: status command reads directly from DB without cross-checking opencode session liveness
   - Mitigation: `isJobStale()` check in status.ts surfaces stale jobs in separate "Stale" section (Phase 25, plan 25-03)

```markdown
## Graceful Reload Contract

### What SIGHUP Does
SIGHUP triggers a graceful drain-and-reload, NOT an immediate shutdown.

Sequence:
1. `shuttingDown = true` and `running = false` are set (stops main poll loop and blocks new launches)
2. In-flight delegation steps finish their current `spawnAndWait()` call before the runner exits
3. Runner re-execs itself with new code via one of two paths:
   - **Under systemd** (`INVOCATION_ID` env var set): exits 0, systemd `Restart=always` restarts it
   - **Bare-metal**: spawns a detached child with same argv before exiting

### What "No New Launches While Draining" Means
Once `shuttingDown = true`:
- The `while (this.running)` loop exits after the current iteration
- `this.launch()` checks `this.shuttingDown` before each step and aborts if true
- No new `getNextPending()` calls occur after the shutdown flag is set

### DB State During Reload
Jobs that were mid-delegation when SIGHUP arrived will be in one of two states after restart:
- **`cancelled`** — if the runner's `launch()` method reached the `cancel(job.id)` call (step loop exited early via `allStepsCompleted = false`)
- **`running`** — if the runner process was killed before `launch()` could clean up

The startup `reconcileStaleJobs()` call handles the `running` case: it resets all running jobs whose IDs are not in the new runner's `activeJobs` (which is empty on startup) back to `pending`.

### Operator Guidelines
- **Preferred reload**: Send SIGHUP — drains cleanly, in-flight steps finish
- **Do NOT use SIGKILL for reload**: leaves jobs stuck in `running` state (reconciler will fix on next startup, but cleaner to drain)
- **If you must hard-restart**: `pilot stop --force` (SIGKILL) then `pilot run` — reconciler handles cleanup
- **Do NOT cancel jobs manually via DB surgery**: reconciler handles it automatically
```
