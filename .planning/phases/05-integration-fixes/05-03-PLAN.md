  <name>Task 1: Fix --once mainLoop to wait for job completion</name>
  <files>src/core/runner.ts</files>
  <action>
The bug is in `mainLoop()` (lines 131-189). The current flow when `--once` is set:

1. Loop iteration 1: scan finds entry → launch it → continue loop
2. Loop iteration 2: scan returns null → enters else branch → `activeJobs.size > 0` → `waitForAnyCompletion()` → continue
3. Loop iteration 3: if job completed, scan returns null → enters else → `activeJobs.size === 0` → **break** (exits loop)
4. Falls to bottom wait-for-completion code (lines 182-189) — but this only executes if we break from the while loop normally

The problem: if ALL launched jobs are still running and a SECOND scan returns null, the code goes to `waitForAnyCompletion()` which waits for ONE job, then continues. This is actually correct for the multi-job case. But there's a subtle issue: the `if (this.opts.once && entry === null)` check at line 173 is DEAD CODE — it can never fire because when `entry === null`, we either waited+continued or broke already in the else branch above.

The REAL issue is more nuanced. When `--once` is set and we launch ONE job:
1. Scan finds entry → launch → falls through to line 173 check: `this.opts.once && entry === null` — FALSE (entry is not null) → continues to `sleep(1000)` → back to top
2. Next scan: nothing new → else branch → `activeJobs.size > 0` → `waitForAnyCompletion()` → continue
3. This actually works IF the detached process exit event fires and reap catches it.

BUT with detached processes, the `exit` event on the child may not fire reliably (noted in decision 03-03). The reap cycle uses `isProcessAlive()` polling. If the process is still alive after `waitForAnyCompletion()` times out (5 min), it returns, rescans, and loops. This works but is slow.

The actual problem described in the requirements: "runner scans queue, launches job, scans again (nothing new), exits". This means the break at line 168 IS being hit, which means `activeJobs.size` is 0 when it shouldn't be. This could happen if:
- The job was launched but `activeJobs.set()` wasn't called yet (race condition in lifecycle mode async fire-and-forget)
- OR the entry was launched via `launchDirectSpawn()` which is async, and by the time scan runs again, the detached process already exited

Looking more carefully: after `launch()` returns, the scan immediately continues. For `launchDirectSpawn()`, the PID IS added to `activeJobs` before the method returns. But for `launchLifecycleMode()`, the method also adds to `activeJobs` before returning. So `activeJobs.size > 0` should be true.

The safest fix: **When `--once` is set, after the scan loop, ALWAYS wait for all active jobs before exiting.** Simplify the logic:

Replace the mainLoop with a cleaner version that separates `--once` behavior:

```typescript
private async mainLoop(): Promise<void> {
  // Track whether we've completed at least one full scan with no launches
  let scannedWithNoLaunch = false;

  while (!this.state.isShuttingDown) {
    await this.reap();
    this.emit('scan');
    const entry = await this.scan();

    if (entry !== null) {
      scannedWithNoLaunch = false;

      if (this.state.activeJobs.size >= this.opts.maxParallel) {
        await this.waitForAnyCompletion();
        continue;
      }

      if (this.opts.dryRun) {
        this.emit('dry-run', entry);
      } else {
        await this.launch(entry);
      }
    } else {
      // No launchable entry found
      if (this.opts.once) {
        // --once: stop scanning for new entries, but wait for running jobs
        break;
      }

      if (this.state.activeJobs.size > 0) {
        await this.waitForAnyCompletion();
        continue;
      }

      // Queue empty and no active jobs — done
      break;
    }

    await sleep(1000);
  }

  // Wait for all active jobs to complete before exiting
  // This is critical for --once mode where we launch then need to wait
  if (!this.state.isShuttingDown) {
    while (this.state.activeJobs.size > 0) {
      await this.reap();
      if (this.state.activeJobs.size > 0) {
        await sleep(2000);
      }
    }
  }
}
```

Key changes:
1. Removed the dead `if (this.opts.once && entry === null)` check
2. When `--once` and no more entries to launch, break immediately (don't loop)
3. The bottom wait-for-all-jobs block now fires for ALL cases (not just `--once`), which is safe — for normal mode the loop only breaks when activeJobs is empty anyway
4. Removed the `if (this.opts.once && ...)` guard on the bottom block — it should wait for all jobs in any exit scenario

```typescript
try {
  // Detect current branch
  const branchResult = await execa('git', ['branch', '--show-current'], { cwd: config.gsdDir });
  const currentBranch = branchResult.stdout.trim() || 'dev';

  // Set upstream tracking if not set (best effort)
  try {
    await execa('git', ['branch', '--set-upstream-to', `origin/${currentBranch}`, currentBranch], { cwd: config.gsdDir });
  } catch {
    // May fail — that's fine, we pull with explicit remote/branch below
  }

  // Pull with explicit remote/branch (works without upstream tracking)
  const result = await execa('git', ['pull', 'origin', currentBranch], { cwd: config.gsdDir });
  const output = result.stdout.trim();
  // ... rest of output handling unchanged
}
```
