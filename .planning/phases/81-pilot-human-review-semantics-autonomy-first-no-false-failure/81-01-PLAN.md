4. **src/core/db.ts** — Add new state transition functions:

   ```typescript
   /**
    * Mark a job as completed pending human review.
    * Sets status to 'completed_pending_review'. Does NOT block the project.
    * Stores optional review checklist in resume_hint for downstream display.
    */
   function markCompletedPendingReview(id: string, reviewChecklist?: string): void {
     const db = getDb();
     db.prepare(`
       UPDATE jobs
       SET status = 'completed_pending_review', completed_at = datetime('now'), resume_hint = COALESCE(?, resume_hint)
       WHERE id = ?
     `).run(reviewChecklist ?? null, id);
     // NOTE: deliberately does NOT call blockProject()
   }

   /**
    * Mark a job as held for mid-phase human review.
    * Sets status to 'review_hold'. Does NOT block the project.
    * Stores the review reason/checklist in resume_hint.
    */
   function markReviewHold(id: string, reviewReason: string): void {
     const db = getDb();
     db.prepare(`
       UPDATE jobs
       SET status = 'review_hold', resume_hint = ?
       WHERE id = ?
     `).run(reviewReason, id);
     // NOTE: deliberately does NOT call blockProject()
   }

   /**
    * Approve a completed_pending_review job, transitioning to completed.
    */
   function approveReview(id: string): void {
     const db = getDb();
     db.prepare(`
       UPDATE jobs
       SET status = 'completed', resume_hint = NULL
       WHERE id = ? AND status = 'completed_pending_review'
     `).run(id);
   }

   /**
    * Resume from review_hold — transition back to running for continued execution.
    * Returns the updated job, or null if not in review_hold.
    */
   function resumeFromReviewHold(id: string): Job | null {
     const db = getDb();
     const result = db.prepare(`
       UPDATE jobs
       SET status = 'running', resume_hint = NULL
       WHERE id = ? AND status = 'review_hold'
     `).run(id);
     if (result.changes === 0) return null;
     return getJob(id);
   }
   ```

5. **src/core/db.ts** — Update `claimNextLaunchable()`: The existing query already correctly excludes blocked projects and projects with running jobs. Review states (`completed_pending_review`, `review_hold`) are terminal-ish — they don't count as "running" in the `SELECT DISTINCT project FROM jobs WHERE status = 'running'` subquery. So claimNextLaunchable already works correctly for `completed_pending_review` jobs (they're not running, so same-project new jobs can launch).

   However, `review_hold` jobs ARE still "active" in a sense — the phase is mid-execution. The `review_hold` status is not 'running', so the same-project exclusion won't apply. This is actually correct: if a phase job is in review_hold, a new independent quick job for the same project should still be able to launch. The dependency system (depends_on) handles ordering between related jobs.

   **No change needed to claimNextLaunchable** — the existing query logic handles it correctly because:
   - `completed_pending_review` is not 'running' → same-project jobs can proceed
   - `review_hold` is not 'running' → same-project independent jobs can proceed  
   - Neither triggers `blockProject()` → project stays 'active'
