<feature>
  <name>Stuck Detection Algorithm</name>
  <files>src/core/stuck.ts, test/core/stuck.test.ts</files>
  <behavior>
The stuck detection algorithm scores processes on 5 independent signals, each with specific point values. Total score determines verdict.

**Signal 1: Log staleness (max 50 points)**
- Log stale > 15min AND runtime > 15min → 30 points
- Log stale > 5min AND runtime > 10min → 20 points
- (These are exclusive — highest matching rule applies)

**Signal 2: CPU usage trend (max 40 points)**
- maxCpu < 0.5% AND runtime > 10min → 25 points
- ALL samples < 0.1% → additional 15 points (cumulative with above)
- CPU sampling: read /proc/pid/stat utime+stime, compute delta between samples

**Signal 3: Session message count (max 40 points)**
- 0 messages AND runtime > 5min → 40 points
- < 3 messages AND runtime > 10min → 20 points

**Signal 4: Memory pressure (max 20 points)**
- Process RSS > 1024MB → 10 points
- System free < 500MB → 10 points

**Signal 5: /proc/pid/status checks (max 80 points)**
- State T (stopped) → 50 points
- State Z (zombie) → 80 points
- wchan matches /read|wait|poll/ AND runtime > 10min → 30 points

**Verdicts:**
- score >= 70 → 'stuck'
- score 40-69 → 'suspect'  
- score < 40 → 'healthy'

**Test cases:**

1. Healthy process (low runtime, active log) → score ~0, verdict 'healthy'
2. Stale log only (15min stale, active CPU) → score 30, verdict 'healthy'
3. Stale log + zero CPU → score 30 + 25 + 15 = 70, verdict 'stuck'
4. Zombie process → score 80, verdict 'stuck' (regardless of other signals)
5. Stopped process → score 50, verdict 'suspect'
6. No messages after 5min → score 40, verdict 'suspect'
7. No messages + stale log → score 40 + 30 = 70, verdict 'stuck'
8. High RSS + low system memory → score 20, verdict 'healthy'
9. stdin-blocked (wchan=read) + stale log → score 30 + 30 = 60, verdict 'suspect'
10. Boundary: score exactly 39 → 'healthy', score exactly 40 → 'suspect', score exactly 70 → 'stuck'
  </behavior>
  <implementation>
Structure the implementation to be testable by separating I/O from logic:

**Helper functions (I/O layer — these read /proc):**
- `getLogStaleness(logFile: string): Promise&lt;number&gt;` — `fs.stat(logFile).mtime`, return seconds since now. Return Infinity if file missing.
- `sampleCpu(pid: number, count: number, intervalMs: number): Promise&lt;number[]&gt;` — Read `/proc/pid/stat`, parse fields 14 (utime) + 15 (stime), sleep intervalMs, read again, compute CPU% for each interval. Return array of CPU percentages.
- `getProcessRss(pid: number): Promise&lt;number&gt;` — Read `/proc/pid/status`, find `VmRSS:` line, parse kB value, convert to MB. Return 0 if unreadable.
- `getSystemFreeMem(): Promise&lt;number&gt;` — Read `/proc/meminfo`, find `MemAvailable:` line, parse kB, convert to MB.
- `readProcState(pid: number): Promise&lt;string | null&gt;` — Read `/proc/pid/status`, find `State:` line, return the letter (R/S/D/Z/T). Return null if unreadable.
- `readProcWchan(pid: number): Promise&lt;string | null&gt;` — Read `/proc/pid/wchan`. Return content or null.

**Scoring function (pure logic, testable with injected data):**
- `computeStuckScore(params: StuckScoreInput): StuckAssessment` where StuckScoreInput contains all pre-fetched signal data
- OR: accept an options object that allows injecting mock data for testing (dependency injection pattern)

**Recommended approach for testability:**
Create an internal `scoreFromSignals(signals: { logStaleness: number, runtime: number, cpuSamples: number[], messageCount: number | null, rssBytes: number, systemFreeMb: number, procState: string | null, wchan: string | null }): { score: number, verdict: string, signals: StuckSignal[] }` that is a pure function. Test this directly.

Then `computeStuckScore(pid, session)` calls the helpers and passes data to `scoreFromSignals`.

Export both for testing flexibility.
  </implementation>
</feature>
