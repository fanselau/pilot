  <behavior>
    The log content analyzer is a pure function that takes an array of log lines (strings, possibly containing ANSI escape codes) and returns matched stuck-signal patterns.

    Three pattern categories with specific regex patterns:

    1. **question** — Process asking questions (waiting for input that will never come):
       - "Would you like me to" (case-insensitive)
       - "Should I" (at word boundary, case-insensitive)  
       - "Do you want" (case-insensitive)
       - "Shall I" (case-insensitive)
       - "Would you prefer" (case-insensitive)

    2. **work_done** — Process declaring work complete but not exiting:
       - "Phase \d+ complete" (case-insensitive)
       - "verification complete" (case-insensitive)
       - "all tests pass" (case-insensitive)
       - "execution complete" (case-insensitive)
       - "plan(ning)? complete" (case-insensitive)

    3. **inapplicable** — Process declaring work not applicable:
       - "not applicable" (case-insensitive)
       - "no web UI" (case-insensitive)
       - "nothing to test" (case-insensitive)
       - "no routes" (case-insensitive)
       - "no browser" (case-insensitive)
       - "skipping.*verification" (case-insensitive)

    Input/output contract for analyzer:
    - `analyzeLogContent(lines: string[])` → `LogContentMatch[]`
    - Each match: `{ category: 'question' | 'work_done' | 'inapplicable', pattern: string, line: string, lineIndex: number }`
    - ANSI escape codes are stripped before matching
    - Empty input → empty output
    - Lines with no matches → empty output

    Input/output contract for Signal 6 in `scoreFromSignals`:
    - Add optional `logContentMatches: LogContentMatch[]` to `StuckSignalInput`
    - Scoring rules (max ~25 points, cumulative across categories):
      - Any `inapplicable` match: +15 points (signal name: `log_inapplicable`)
      - Any `work_done` match: +10 points (signal name: `log_work_done`)
      - Any `question` match: +10 points (signal name: `log_question`)
      - Max cap: 25 points total for log content signal
    - The signal detail includes the matched line text (truncated to 60 chars)

    Reason field in StuckAssessment:
    - Add `reason?: string` to StuckAssessment interface
    - When log content signals fire, generate a human-readable reason string, e.g.:
      "Process declared verification not applicable 65m ago but hasn't exited"
      "Process asked 'Would you like me to...' 30m ago — likely waiting for input"
      "Process declared work complete 45m ago but hasn't exited"
    - Reason combines the log content category with the log staleness time
    - When no log content signals → reason is undefined

    Updated computeStuckScore orchestrator:
    - Read last 50 lines of the log file (after existing getLogStaleness call)
    - Strip ANSI codes, pass to analyzeLogContent
    - Include matches in StuckSignalInput for scoring
    - Generate reason string for StuckAssessment output

    Cases:
    - `analyzeLogContent([])` → `[]`
    - `analyzeLogContent(["normal log line"])` → `[]`
    - `analyzeLogContent(["Would you like me to continue?"])` → `[{category: 'question', ...}]`
    - `analyzeLogContent(["Phase 3 complete"])` → `[{category: 'work_done', ...}]`
    - `analyzeLogContent(["Verification not applicable"])` → `[{category: 'inapplicable', ...}]`
    - `analyzeLogContent(["\x1b[32mPhase 3 complete\x1b[0m"])` → `[{category: 'work_done', ...}]` (ANSI stripped)
    - `scoreFromSignals({...healthy, logContentMatches: [{category: 'inapplicable', ...}]})` → score includes 15 pts
    - `scoreFromSignals({...healthy, logContentMatches: [{category: 'inapplicable'}, {category: 'work_done'}]})` → score includes 25 pts (capped)
  </behavior>
