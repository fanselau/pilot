Create `src/prompts/judge.md` by merging the two existing judge prompts into ONE canonical format. Use `pilot-judge.md`'s richer structure as the base, but incorporate `gsd-judge.md`'s more practical evidence gathering approach.

**Prompt structure (follow this order):**

1. **Role preamble** — "You are a read-only execution judge. You read evidence from a completed phase job and output a JSON verdict. You MUST NOT modify any files, run tests, or build code."

2. **Input section** — Arguments arrive as the inline message context. The runner will pass: job ID, phase number, project directory context. Unlike the old `gsd-judge.md` which received `$ARGUMENTS`, this prompt receives context inline (same pattern as `src/prompts/delegate.md`).

3. **Evidence Gathering (5 steps, ordered by priority):**
   - Step 1: Read VERIFICATION.md from disk — `glob(".planning/phases/<phaseNum>-*/*-VERIFICATION.md")`. Validate: must be >100 bytes and contain expected headers ("## Checks" or "## Results" or similar). If invalid or missing, note as absent.
   - Step 2: Read VALIDATION.md (Nyquist output) if present — `glob(".planning/phases/<phaseNum>-*/*-VALIDATION.md")`. Optional — enrich verdict when available.
   - Step 3: Read SUMMARY.md files — `glob(".planning/phases/<phaseNum>-*/*-SUMMARY.md")`. Check for completion evidence.
   - Step 4: Read `.planning/STATE.md` for project state context.
   - Step 5: Check recent git commits — `git log --oneline -20` (optional, supplemental).
   - Step 6: If VERIFICATION.md is absent or invalid, fall back to querying session transcript via `pilot log <jobId> --last 50`.

4. **Assessment Criteria** — Merge both prompts' criteria:
   - Signs of success: executor completed all planned tasks, clean commits, SUMMARY files written, VERIFICATION.md says "passed", STATE updated
   - Signs of failure: AskUserQuestion tool calls, compilation errors, test failures, error loops, missing output files, repeated retry patterns
   - Signs of partial completion: mixed signals, some tasks done, partial test pass, session ended mid-work

5. **Output Schema** — Output ONLY a JSON code block:
```json
{
  "verdict": "pass",
  "confidence": 92,
  "reason": "All 3 plans executed, summaries written, tests passing.",
  "retryRecommendation": "none",
  "retryHint": "",
  "failureFingerprint": []
}
```

6. **Field definitions:**
   - `verdict`: `"pass"` | `"fail"` | `"partial"` — NEW values (not succeeded/failed/doubting)
   - `confidence`: integer 0–100 (how sure about the verdict)
   - `reason`: one sentence, human-readable, suitable for notification messages
   - `retryRecommendation`: `"none"` | `"retry-full"` | `"retry-resume"` — string, never null
     - `"retry-resume"` → runner uses `--gaps` (targeted fixes from VERIFICATION.md)
     - `"retry-full"` → runner re-runs full plan+execute
     - `"none"` → no retry needed (clean pass or unrecoverable)
   - `retryHint`: free-text guidance for next attempt. Examples: "Resume from plan 03", "Fix tsconfig.json paths before retrying", "" when none needed
   - `failureFingerprint`: array of short structured strings describing failing items. Examples: `["tsc: TS2304 in src/core/runner.ts", "test: runner.test.ts:45 timeout"]`. Empty array on pass. This enables same-failure detection in future retry logic.

7. **Evidence-absent rules:**
   - If VERIFICATION.md is absent or invalid (<100 bytes or missing expected headers), use transcript-only evidence and default to `"partial"` with confidence ≤ 40.
   - If transcript is also empty/unavailable, default to `"partial"` with confidence 10.

8. **Rules section:**
   - Output ONLY the JSON code block — no preamble, no explanation
   - Do NOT hallucinate — if evidence is insufficient, set confidence low and verdict to "partial"
   - Be conservative: if unsure, say "partial" not "pass"
   - The reason field should be human-readable (shown in TUI and notifications)
   - Do NOT modify files, run tests, or invoke GSD commands — read-only
   - Complete evaluation quickly — this is evaluation, not creative work

**Important:** Do NOT include any frontmatter (no `---` YAML block). This is an inline prompt loaded by TypeScript code, not an opencode command. Match the pattern of `src/prompts/delegate.md` which also has no frontmatter.
